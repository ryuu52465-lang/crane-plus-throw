## 4. 時系列の記録

### 4.1 Day1: アームを動かす（10/28）

1. 実習のコンテナ `pai_ros2` を起動。ROS2 Humble、Gazebo、CRANE+の書籍パッケージ、YOLOが入っていることを確認した
2. 書籍の `crane_plus_with_table.launch.py` でGazeboを起動し、関節の軌道指令で振る動作を試した
3. **つまずき: 画面ではアームが動いていないように見えた**
   - 原因: 見ていたのはRViz（MoveIt用の画面）で、Gazeboではなかった。関節角を記録したら、実際には動いていた
4. **つまずき: 振りかぶりが「少し後ろに曲がるだけ」に見えた**
   - 原因: 関節によって曲がる向きの正負が逆。joint2（肩）は+で前傾、joint3（肘）・joint4（手首）は+で**後ろ**に曲がる（URDFの回転軸がjoint2は+y、joint3は-y）
5. URDFから可動範囲と速度上限を確認した
   - joint2: -1.83〜+1.78rad、joint3: -2.56〜+2.45rad、joint4: -1.84〜+1.77rad
   - 速度上限: 全関節2.0rad/s（実機のサーボの仕様）

### 4.2 Day2: つかんで投げる（10/28）

1. 自作パッケージ `crane_plus_throw` を作成した（urdf、world、launch、throw_node）
2. **つかむ方法**: Gazeboの **DetachableJoint**（attach/detachの指令で物体を手先に固定・解放する機能）を使った。グリッパーの摩擦でつかむとすべって不安定になるため
3. **つまずき: ロボットがワールドに出てこない**
   - 原因: Gazeboがワールドを読み込んでいる途中にロボットの追加を頼むと、「OK」が返っても捨てられることがある
   - 対策: ロボットがワールドに現れるまで追加を繰り返す
4. 最初の投げ（肩・肘・手首を同時に振り、上限2rad/sで振る）: 着地は約15cm。着地後に転がって箱の壁で止まっていた
5. 離す角度を -0.9〜+0.45rad で変えても、最初の着地点は最大16cm程度
6. **スナップ投げ（ユーザー発案）**:
   - 振りかぶり: 肩-1.3、肘+1.3、手首+1.0（後ろに反る）
   - 肩・肘が先に振り出し、手首は0.15秒遅れて動き出す
   - 3関節すべてが2rad/sで動いている瞬間に、真上（全関節0）を通るよう、通過点に速度も指定した
   - 真上で離す（このとき同時にグリッパーも開く）
   - 結果: 最高点 1.27m → **1.355m**、最初の着地点 0.16m → **0.30m（約2倍）**
7. **つまずき: Gazeboが4つ同時に動いていた**
   - 原因: `bash -c` の中で `pkill -f "ros2 launch"` を使ったら、実行中のシェル自身にもマッチして自分を止め、後続の停止処理が走らなかった
   - 影響: 時刻の逆戻り、古いブリッジとの混線、attachの不調
   - 対策: `tools/restart_sim.sh` で全プロセスを止めてから起動する（パターンに `[r]os2` のように[]を入れて自分にマッチしないようにする）
8. 箱を着地点に置き、3回中2回が箱に入った

### 4.3 Day3（前倒し）: AIを入れる（10/28）

#### (A) YOLOで見る
1. 机の真上0.6mから見下ろすカメラ（640×480、水平画角1.0rad）をワールドに追加した
2. YOLOv8n（COCOで学習済み）でシミュレーション画像を推論したところ、オレンジの球を **「sports ball」と信頼度0.77で検出** できた
   - ロボット本体が「cell phone」と誤検出されたが、sports ballだけを使うので問題ない
3. 画像座標から机の上の座標への変換（ピンホールカメラモデル）: 手で検算して、ボールの実際の位置と一致した
4. 青い箱はAIを使うまでもないので、色（HSV）で検出する

#### (B) 投げ方を学習する
1. 試投を自動で繰り返し、着地点を記録する仕組み（collect_data）を作った
2. **つまずき: ボールを元の位置に戻しても、転がる勢いが残る**
   - 原因: Gazeboの set_pose は位置しか変えず、速度・回転はそのまま残る。転がっていたボールは戻した後も動き続け、つかもうとして物理計算が破綻した（ボールが54m先まで飛んだこともあった）
   - 対策: **静止しているアームにボールを一瞬attachしてからdetachする**と、速度も回転も0になる。そのあとで位置を戻す
3. **つまずき: ボールの位置がROSで取れない**
   - 原因: ros_gz_bridge で pose/info を変換すると、物体の名前が消える。PosePublisherのモデル単位の位置も、このバージョンでは出なかった
   - 対策: ボールに **OdometryPublisher** を付けて、ワールド座標を `/model/ball/odometry` に出す
4. **つまずき: 振りかぶると最高点が6cm下がった**
   - 原因: 後ろに飛んだボールを止めるために机の後ろの縁（x=-0.10）に立てた柵に、振りかぶったアームが当たっていた
   - 対策: 後ろの柵を外した（戻す処理はアームでボールを止める方式なので、柵がなくても困らない）
5. **試行錯誤: 何を変えて距離を狙うか**
   - 案1: **離す角度**を -0.4〜+0.4rad で変える（30回投げた） → 着地距離が **20〜25cmの間でしか変わらず**、ばらつきも大きい。箱の内寸12cmより狭いので、狙い分ける意味がない → **不採用**（データ: `data/release_angle_data.csv`）
   - 案2: 離すのはいつも真上で、**振る速さ**を0.8〜2.0rad/sで変える → 採用
6. **つまずき: 同じ速さでも結果が2パターンに分かれる／4回に1回くらい後ろに飛ぶ**
   - 調べたこと:
     - DetachableJointの状態トピックを見て、attach/detachは正しく切り替わっていることを確認した
     - つかむ前にattachしたり、グリッパーを全開にしたり、ボールとロボットの衝突を切ったりしたが、直らなかった
     - 関節角を時系列で記録した結果、**手首（joint4）が可動範囲の下限 -1.84rad に張り付いて、ずっと動いていない**ことがわかった（ユーザーも、見ていて「手首のスナップが入っていない」と指摘）
   - 原因: つかむ前に真上で待つ姿勢を逆運動学で計算すると、手首が **-1.94rad**（下限 -1.84radの外）になっていた。範囲外を指令すると手首が下限に張り付き、その後の振りかぶりの位置指令に追従しなくなる
   - 対策: 手先を真下（-90°）から3°ずつ傾けて、**全関節が可動範囲に収まる姿勢**を探す（書籍の `joint_in_range` で判定）
   - 結果: 手首が+1.0radまで後ろに反ってから振り抜けるようになり、2.0rad/sでの着地距離が15.7cm → **27.2cm** に伸びた。ばらつきもほぼ消えた
   - このとき入れた「先にattachしてから指を軽く添える」「ボールとロボットの衝突グループを分ける」は、手首とは別の対策としてそのまま残している（指がボールを押し上げたり、ボールと手の重なりで力がかかったりするのを防ぐ）
   - 手首が張り付いていたときのデータ: `data/speed_data_wrist_stuck.csv`（参考）
7. 箱を内寸8cmに小さくして、狙う精度に意味が出るようにした

## 5. 結果

### 5.1 学習データと学習結果（`data/throw_data.csv`、`docs/images/throw_model.png`）
- 振る速さ0.8〜2.0rad/sでランダムに40回投げた → **40回とも正常に前へ着地**（外れ値0件）
- 振る速さと着地距離はほぼ一直線の関係: 0.89rad/s で 16.1cm → 1.95rad/s で 26.6cm
- モデル: 多層パーセプトロン（入力1→16→16→出力1、tanh）。入力は振る速さ、出力は着地距離
  - 5件に1件を検証用に取っておき、学習には残りを使った
  - 平均誤差: 学習 **0.10cm** ／ 検証 **0.38cm**
  - 狙える距離: **15.4〜26.9cm**
- 使い方: 箱までの距離が与えられたら、振る速さ0.8〜2.0rad/sを801通り試して、予測距離が一番近い速さを選ぶ（逆算）

### 5.2 AIで狙って投げる評価（`data/eval_result_2026-10-28.txt`）
- 箱とボールを毎回ランダムに配置して10回試した → **成功率 10/10**
- 箱の距離は17〜25cm、左右の向きもばらばら。モデルが選んだ振る速さは1.04〜1.68rad/s
- カメラから見積もった箱の位置と正解の差は **2〜3mm**
- YOLOのsports ballの信頼度は0.45〜0.77程度だった（シーンによって変わる）

## 6. レポートに書ける工夫点（候補）

1. **実機と同じ制約のまま投げる**: 速度上限2rad/sを変えず、そのぶん関節の動かし方で飛距離を稼いだ。実物のCRANE+でもそのまま再現できる設計（実用性）
2. **手首のスナップ（人の投げ方を参考に）**: 肩・肘を先に振り、手首を遅らせて溜めてから振り抜く。全関節が最高速の瞬間に真上を通るよう、軌道の通過点に速度を指定した → 飛距離が約2倍
3. **ロボット自身の試投データから学ぶ（Physical AI）**: 試投→着地を記録、を自動で40回繰り返し、MLPで「振る速さ→着地距離」を学習した。物理の式を手で立てなくても、データから狙いを決められる
4. **見て狙う**: YOLOでボールを、色で箱を見つけ、画像座標から机上の座標へ変換した（誤差2〜3mm）
5. **自動で実験を回す仕組み**: ボールの勢いをアームで止めてから戻す方法、正解データ（odometry）で着地点を自動判定する仕組みで、人の手を介さず何十回も試投できるようにした
6. **試行錯誤のプロセス**: 離す角度では幅が狭く不採用 → 振る速さに変更。手首の張り付きを関節角の時系列記録から突き止めた

## 7. 反省・考察（候補）

- 飛距離15〜27cmは小さい。速度上限を上げれば伸びるが、実機での再現性を優先した
- 学習モデルは1入力（振る速さ）のみ。ボールのつかみ位置や投げる向きの影響は入れていない（今回は対称性で向きは関係ない前提）
- 物理シミュレーションなので試投の再現性が非常に高い（同じ条件なら着地がmm単位で一致）。実機ではばらつきが大きくなるはずで、その場合はデータ数を増やす、あるいは不確かさも推定するモデルが必要
- 箱の検出は色に頼っている。物体の種類が増えるならYOLOの追加学習が必要
- YOLOはシミュレーションの単純な球でも「sports ball」と判定できたが、信頼度は0.45〜0.77とばらつく
- 時間がかかったのは、制御よりも**シミュレータの癖**（プロセスの多重起動、set_poseで速度が残る、手首の可動限界での張り付きなど）の切り分けだった
